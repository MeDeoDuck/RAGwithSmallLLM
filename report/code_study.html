GPT-small 구조

빈칸들이 어디에 들어가는지 보려면 전체 그림이 먼저 필요합니다. 아래는 model.py의 실제 모듈 이름과 노트북 셀 7이 고르는 설정(hidden 512 / 4 layer / q head 16 / kv head 4 / head_dim 32 / 컨텍스트 1024 / rope_theta 20000)을 그대로 옮긴 것입니다.

전체 스택

B = 배치, S = 시퀀스 길이. 레이어를 통과하는 동안 (B, S, 512) 모양은 변하지 않습니다. 모양이 바뀌는 곳은 입구(embed)와 출구(lm_head) 둘뿐입니다.

TransformerLayer 하나의 내부 — Pre-Norm

정규화가 residual 경로 밖에 있습니다(Pre-Norm). 그래서 입력 x가 덧셈만 거쳐 출력까지 곧장 이어지고, 기울기가 감쇠 없이 흐릅니다. 원 Transformer 논문의 Post-Norm Norm(x + Sublayer(x))은 깊어지면 warmup에 민감해져 현대 LLM은 대부분 이 배치를 씁니다. 빈칸 8이 이 구조를 짜는 문제였습니다.

MultiHeadAttention 내부 — GQA의 모양 흐름

query는 16 head인데 key/value는 4 head만 만들고(빈칸 5), repeat_kv가 4배 복제해 짝을 맞춥니다. KV 캐시와 projection 파라미터가 1/4이 됩니다. MHA로 짰다면 레이어당 attention 파라미터가 655,360 → 1,048,576으로 늘어납니다. 점수 계산·마스크·softmax·head 합치기가 빈칸 6, 마스크 생성이 빈칸 9입니다.

apply_rotary_emb — RoPE 적용

RoPEmodel.py:66
문제 — 위치 m의 query/key 벡터를 각 θᵢ에 대해 2차원 회전시킨다. 주어진 shape 힌트: cos,sin은 (B, S, D/2), x는 (B, H, S, D).
[x₁′, x₂′] = [x₁·cos − x₂·sin, x₁·sin + x₂·cos]
정답 코드 보기
cos = cos.unsqueeze(1)  # (batch_size, 1, seq_len, head_dim // 2): broadcast over heads
sin = sin.unsqueeze(1)
x1, x2 = x.chunk(2, dim=-1)  # (x1[i], x2[i]) is the 2D pair rotated by angle m * theta_i
x = torch.cat([x1 * cos - x2 * sin, x1 * sin + x2 * cos], dim=-1)
왜 이렇게 되는가
  • 왜 회전인가. 회전 후 내적이 ⟨R_m q, R_n k⟩ = f(q, k, m−n)이 되어 상대 위치에만 의존한다. 절대 위치 임베딩을 더하는 방식과 달리 길이 외삽에 유리하다.
  • unsqueeze(1)의 이유. cos/sin에는 head 축이 없다. 1을 끼워 넣으면 16개 head 전부에 같은 각도가 broadcast된다.
  • 앞/뒤 절반 쌍 vs 인접 쌍. 논문 원형은 (x₀,x₁),(x₂,x₃)… 처럼 인접 원소를 묶지만, 여기서는 HuggingFace Llama와 같은 앞절반/뒤절반 방식을 썼다. q와 k에 같은 순열을 적용하는 것이라 내적 값은 동일하고, 처음부터 학습하는 모델이라 표현력 차이도 없다. 대신 slicing 비용이 적고 HF Llama와 수치 비교로 검증할 수 있다.
검증된 사실 — (m,n)=(10,4)와 (106,100), (500,494)의 내적이 소수 5자리까지 동일 — 상대성 확인. 회전이 노름을 보존하는 것도 확인.

RMSNorm.forward

정규화model.py:91
문제 — RMS 정규화를 구현한다.
RMSNorm(x) = x / √(mean(x²) + ε) ⊙ γ
정답 코드 보기
input_dtype = x.dtype
x = x.to(torch.float32)  # compute the statistics in fp32 for numerical stability
variance = x.pow(2).mean(-1, keepdim=True)
x = x * torch.rsqrt(variance + self.eps)
output = self.weight * x.to(input_dtype)
왜 이렇게 되는가
  • LayerNorm과의 차이. 평균을 빼지 않고 bias도 없다. 스케일만 맞추므로 연산이 더 싸고, 실제로 성능 저하 없이 동작한다는 것이 RMSNorm 논문의 주장이다.
  • fp32로 올리는 이유가 핵심이다. 노트북이 모델을 bfloat16으로 캐스팅해 학습한다(model_dtype="cast_bf16"). bf16은 가수부가 7비트뿐이라 제곱 평균을 bf16으로 누적하면 오차가 크고, 그 값으로 나누는 정규화가 오차를 증폭시킨다. 통계만 fp32로 계산하고 원래 dtype으로 되돌린다.
  • torch.rsqrt는 역제곱근을 한 번에 계산한다. 1/torch.sqrt(...)보다 빠르다.

RotaryEmbedding.__init__ — 주파수 초기화

RoPEmodel.py:112
문제 — 회전 각속도 inv_freq를 계산해 버퍼로 등록한다.
θᵢ = base^(−2i/d), i = 0 … d/2−1, base = rope_theta (노트북에서 20000.0)
정답 코드 보기
base = config.rope_theta
dim = config.head_dim
# theta_i = base^(-2i / head_dim), i = 0, 1, ..., head_dim // 2 - 1
inv_freq = 1.0 / (base ** (torch.arange(0, dim, 2, dtype=torch.int64).to(device=device, dtype=torch.float) / dim))
왜 이렇게 되는가
  • 왜 지수적으로 감소하는가. i가 커질수록 θᵢ가 작아져 회전이 느려진다. 낮은 차원은 빠르게 돌아 가까운 위치를 구분하고, 높은 차원은 느리게 돌아 먼 위치를 구분한다. 여러 주파수를 겹쳐 위치를 인코딩하는 구조다.
  • shape 힌트와 다르게 1차원으로 만든 이유. 주석은 (1, head_dim//2)라고 하지만, 빈칸 아래의 원본 forward가 self.inv_freq[None, :, None] 형태로 1차원 텐서를 전제한다. 2차원이면 expand에서 에러가 난다. 원소 개수는 힌트와 같다.
  • persistent=False 버퍼라 체크포인트에 저장되지 않고 로드할 때마다 재계산된다. transformers 5.x에서는 이 재계산이 깨져 초기화되지 않은 메모리가 들어가는 문제가 있어 버전을 4.52.4로 고정했다.

RotaryEmbedding.forward — cos/sin 계산

RoPEmodel.py:132
문제 — 위치 × 주파수로 각도를 만들고 cos, sin을 낸다.
freqs[b, s, i] = position[b, s] × θᵢ → cos(freqs), sin(freqs)
정답 코드 보기
freqs = (inv_freq_expanded.float() @ position_ids_expanded.float()).transpose(1, 2)  # m * theta_i
cos = freqs.cos()

왜 이렇게 되는가

MultiHeadAttention.__init__ — Q/K/V/O projection

GQAmodel.py:153
문제 — query·key·value·output projection을 선언한다. key/value는 num_key_value_heads개만 만든다.
정답 코드 보기
self.q_proj = nn.Linear(config.hidden_size, config.num_attention_heads * self.head_dim, bias=False)
self.k_proj = nn.Linear(config.hidden_size, config.num_key_value_heads * self.head_dim, bias=False)
self.v_proj = nn.Linear(config.hidden_size, config.num_key_value_heads * self.head_dim, bias=False)

왜 이렇게 되는가
  • GQA의 핵심. query head는 16개지만 key/value head는 4개만 만든다. forward의 repeat_kv가 K/V를 4배 복제해 16개 query head와 짝을 맞춘다. KV 캐시 크기와 파라미터가 1/4로 줄어드는 대신 성능 저하는 작다는 것이 GQA 논문의 요지다.

  • 이름을 마음대로 정할 수 없다. q_proj는 원본 TransformerForCausalLM.forward가, k_proj/v_proj는 이 클래스의 forward가 참조한다. 출력 projection은 Llama 관례대로 o_proj로 했다.

MultiHeadAttention.forward — attention 계산

Attentionmodel.py:196
문제 — scaled dot-product attention을 계산하고 head를 합쳐 o_proj를 통과시킨다.
Attention(Q, K, V) = softmax(QKᵀ/√d_k + M) · V, scale = head_dim^(−0.5)
정답 코드 보기
attention_weights = torch.matmul(query_states, key_states.transpose(2, 3)) * self.scale
if attention_mask is not None:
    attention_weights = attention_weights + attention_mask  # additive mask: 0 = keep, dtype min = masked
attention_weights = F.softmax(attention_weights, dim=-1, dtype=torch.float32).to(query_states.dtype)
attention_weights = F.dropout(attention_weights, p=self.dropout, training=self.training)
attn_output = torch.matmul(attention_weights, value_states)  # (batch_size, num_attention_heads, seq_len, head_dim)
attn_output = attn_output.transpose(1, 2).contiguous().reshape(batch_size, seq_len, -1)
attn_output = self.o_proj(attn_output)
왜 이렇게 되는가
  • 마스크를 더하는(additive) 이유. 빈칸 9에서 만드는 마스크는 허용 위치가 0, 차단 위치가 finfo(dtype).min인 형태다. softmax 전에 더하면 차단 위치의 exp가 0에 수렴한다. −inf 대신 dtype 최솟값을 쓰는 이유는 다음 항목에서 설명한다.
  • softmax를 fp32로. bf16에서 exp와 합산을 하면 정밀도가 부족하다. dtype=torch.float32로 계산한 뒤 원래 dtype으로 되돌린다.
  • transpose(1,2).contiguous().reshape — (B,H,S,D)를 (B,S,H·D)로 합친다. transpose는 메모리 배치를 바꾸지 않으므로 contiguous() 없이는 reshape가 실패한다.
  • KV 캐시. 빈칸 위 원본 코드가 이전 key/value를 이어 붙이므로 key 길이는 S + cache_len이다. 생성 단계에서는 S=1이고 T가 지금까지 길이가 된다.
검증된 사실 — 마지막 토큰을 바꿔도 이전 위치 logits가 전혀 변하지 않음(diff 0.0) — causal 확인. KV 캐시 greedy 생성이 캐시 없는 생성과 토큰 단위로 동일.

FeedForwardNetwork.forward — SwiGLU

FFNmodel.py:224
문제 — 원본 __init__이 선언해 둔 gate_proj, up_proj, down_proj, SiLU를 조합한다.
FFN(x) = W_down( SiLU(W_gate x) ⊙ W_up x )
정답 코드 보기
# SwiGLU: down(SiLU(gate(x)) * up(x))
outputs = self.down_proj(self.act_fn(self.gate_proj(x)) * self.up_proj(x))
outputs = self.dropout(outputs)
왜 이렇게 되는가
  • 게이팅 구조. 일반 FFN은 W₂(act(W₁x))인데, SwiGLU는 경로를 둘로 나눠 한쪽에 활성함수를 걸고 원소별 곱으로 합친다. 게이트가 어떤 성분을 통과시킬지 학습한다.
  • SiLU(= Swish) x·σ(x)는 ReLU와 달리 음수 구간에서 완전히 죽지 않아 기울기가 더 잘 흐른다.
  • dropout(ffn_dropout, 노트북 0.05)은 residual에 더해지기 직전인 FFN 출력에 건다.

_prepare_attention_mask — causal + padding

Attention maskmodel.py:385
문제 — causal 마스크와 padding 마스크를 합쳐 (batch, 1, seq_len, target_len) additive 마스크를 만든다.
정답 코드 보기
min_dtype = torch.finfo(dtype).min
# causal: query i (absolute position seen_token_length + i) can attend to key j only if j <= seen_token_length + i
query_positions = torch.arange(sequence_length, device=device) + seen_token_length
key_positions = torch.arange(target_length, device=device)
allowed = key_positions[None, :] <= query_positions[:, None]  # (sequence_length, target_length)
allowed = allowed[None, None, :, :].expand(batch_size, 1, sequence_length, target_length)
# padding: never attend to padded keys (attention_mask == 0)
if attention_mask is not None:
    allowed = allowed & attention_mask[:, None, None, :].to(device=device, dtype=torch.bool)
mask = torch.zeros((batch_size, 1, sequence_length, target_length), dtype=dtype, device=device)
mask = mask.masked_fill(~allowed, min_dtype)
왜 이렇게 되는가
  • 두 가지를 합친다. ① causal — query i는 자기 자신과 이전 토큰(key j ≤ i)만 본다. ② padding — attention_mask == 0인 pad key는 어떤 query도 못 본다.
  • KV 캐시가 있으면 위치가 밀린다. query의 절대 위치가 seen_token_length + i이므로 그만큼 이동시켜야 한다. 이걸 빼먹으면 캐시를 쓸 때만 조용히 틀린다.
  • −inf가 아니라 finfo.min을 쓰는 이유. left padding에서는 모든 key가 막힌 행이 생길 수 있다. −inf로 채우면 softmax가 exp(−inf)/Σexp(−inf) = 0/0 = NaN을 내고 그 NaN이 역전파로 전체를 오염시킨다. dtype 최솟값을 쓰면 그 행은 균등분포로 퇴화할 뿐 NaN이 나지 않는다. 어차피 그 위치의 출력은 loss에서 −100으로 제외된다.
  • head 축을 1로 두면 16개 head에 broadcast된다. 메모리를 16배 아낀다.
검증된 사실 — S=6까지 넣고 캐시를 만든 뒤 S=4를 이어 넣은 결과가, 10개를 한 번에 넣은 결과와 diff 0.0으로 일치 — 위치 오프셋이 정확하다는 증거. 전부 pad인 행도 NaN 없이 통과.

  • 여기까지가 빈칸의 범위다. JSON 파싱 같은 정교한 후처리는 핸드아웃 4.2.1에서 직접 설계할 부분이라 별도 모듈(rag_parsing.py)로 분리했다.
검증된 사실 — 이 한 줄 덕에 naive RAG의 ROUGE-1이 핸드아웃 참고값 0.1526보다 높은 0.2124로 나왔다.

전체를 관통하는 설계 원칙 4가지

정밀도는 필요한 곳에서만 올린다

모델 전체는 bf16으로 돌리되, 통계와 확률을 다루는 세 곳만 fp32로 올린다 — RMSNorm의 제곱평균(2), RoPE의 각도(4), attention softmax(6). 나누기와 지수함수가 오차를 증폭시키는 지점들이다.

학습과 추론의 입력 분포를 같게 만든다

RAG 학습 프롬프트(16)와 추론 프롬프트(12)가 글자 단위로 같은 템플릿이고, 768토큰 예산도 같다. zero-shot 능력이 없는 63M 모델에서는 이 일치가 성능을 좌우한다.

left padding이 곳곳을 규정한다

분류가 마지막 위치로 판단하고(15) decoder가 오른쪽 끝에서 생성하므로(13), 패딩은 반드시 왼쪽이다. 그 결과 “전부 마스크된 행”이 생기고, 그래서 마스크를 −inf가 아닌 finfo.min으로 채워야 한다(9). 세 빈칸이 하나의 제약으로 엮여 있다.

빈칸 밖의 코드가 빈칸의 답을 결정한다

inv_freq를 1차원으로 만들어야 하는 것(3), loss를 모델 안에서 shift해야 하는 것(10), o_proj라는 이름(5), 길이를 1024로 고정해야 하는 것(14) — 전부 이미 주어진 코드가 무엇을 전제하는지를 읽어야 알 수 있다. 빈칸만 보고 짜면 틀린다.
